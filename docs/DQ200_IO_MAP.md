# DQ200_G2 (`0CW300043H_0002`, TC1784): карта входов/выходов, ПО безопасности, состояние «ТКУ в контуре»

Дата: 2026-11-01/02. Прошивка не изменялась; RAM прошивки только читалась (наблюдение). Метки — как в
`docs/SIMOS18_GPTA_IO_RE.md` §0: `VERIFIED-S` (статически по образу), `VERIFIED-T` (трасса/эмулятор),
`HYP`, в коде — `UNVERIFIED`. Документ заменяет таблицы MO и АЦП `DQ200_G2_REVERSE_ENGINEERING_CHECKPOINT.md`
§2–§3 там, где они расходятся.

## 0. Кратко

- Доказано: каналы Pwm клапанов → ячейки GPTA, группировка 8 клапанов в 2 модуля по 4, датчик тока каждого
  канала → вход АЦП, токовые ПИ-регуляторы 3 кГц, отключение выводов клапанов ПО безопасности, список MO CAN,
  условия переходов главного автомата 1→2→3→4, порог «давление достаточно», расшифровка DTC по таблицам
  прошивки, обратное чтение линии P2.1 на ADC[23].
- 2026-11-02 (второй проход): FADC TC1784 эмулирован (`tc1784_io::fadc`, §5.2), внешнее устройство SSC1/P2.8
  подключено как устройство контроля силовых каскадов (идентификация, два канала сторожа «вопрос-ответ», ключ
  питания ADC[30]/[31] по сторожу и выводам P3.9/P3.10/P1.13, §5.1). ПО безопасности разрешает выходы через
  ~0.1 с и больше не отключает их; все его тесты пути отключения (группа 6, шаги 0x02..0x35) и тест ключа
  питания (группа 1) проходят; ошибок ПО безопасности 0, программных сбросов 0 (`VERIFIED-T`).
- В контуре (studio, ЭБУ + ТКУ + plant): ТКУ проходит WFS5, принимает CAN ЭБУ/шасси, выходы разрешены, автомат
  1→2→3 (уже через 0.3 с, без вращения двигателя — переход по `0xD0004D1B`), прошивка ведёт клапаны своими
  токовыми регуляторами (до 1.12 А), 3→4 на ≈ 17 с (давление ≥ ~23 бар при 0 °C). В состоянии 4 прошивка
  работает всеми 8 клапанами, а давление падает до 0–4 бар: насос V401 не запускается (разгон без датчиков
  обрывается, нет сигнала вращения на IN47, §4).
- Третий проход (2026-11-02): драйвер насоса на P3.6 и бездатчиковый БК-мотор V401 смоделированы (§4); прошивка
  сама синхронизирует мотор, держит 2610 об/мин и набирает 20 → 58 бар, выключает/включает насос в полосе
  ≈ 42..58 бар. Датчики вилок по характеристике CAL (§6), функции 8 клапанов (§3.1) — четыре вилки держатся
  прошивкой в нейтрали. Главный автомат: 3 → 4; 4 → 5 не проходит (`0xD0007E1B` = 5 вместо 3, §7).
- Четвёртый проход (2026-11-02): (1) назначение клапанов доказано статически по таблицам прошивки — 2/4 и N440
  были перепутаны (§3.1); (2) характеристика датчиков хода сцеплений — из CAL прошивки (29 мм на 10..90 %),
  монитор P0810 разобран, золотники plant следуют току катушек модели платы, порог клапанов сцеплений и точки
  касания из адаптаций — P0810 на стенде больше нет, подкоробки не отключаются, первичные валы в нейтрали стоят
  (§6.1); (3) расхождение Unicorn/native — задержка прерываний до конца кванта на Unicorn ломала надзор ПО
  безопасности за 10-мс задачей (ошибка 0x17 = «бит 23») → сброс; исправлено, оба бэкенда идут одинаково (§5.3).
- Не достигнуто (четвёртый проход): включение передач (вилки остаются в нейтрали, активны P0914/P0919), поэтому
  `0x7E1B` ≠ 3 и нет перехода 4 → 5 / готовности 8, D, трогания и переключений (§8).
- Пятый проход (2026-11-02, §11): прошивка сама включает 1-ю и R в P (состояние 5 на 1.4 с), после D — состояние 9,
  трогается на K1 со скольжением и переключает 1 → 2 → 3 (→ 4 → 5 при длинном прогоне) на шасси-стенде, оба бэкенда
  одинаково, сбросов ТКУ нет. Четыре причины: тест селектора (P0914/P0919), микросхемы драйверов клапанов на SSC0,
  насыщение датчиков вилок и перепутанные типы клапанов сцепление ↔ давление подкоробки.

### 3.1 Функции клапанов (четвёртый проход, 2026-11-02: `VERIFIED-S`)

Слой выходов клапанов `0x800CDA02` перебирает исполнители 0..7: номер клапана — таблица `0x8013A0FC` =
`[0, 1, 4, 5, 6, 7, 2, 3]`, тип исполнителя — `0x8013A104` = `[0, 0, 1, 1, 1, 1, 2, 2]`; `0x800E68E8` переводит
номер клапана в регулятор тока по `0x8013C9C4` = `[0, 1, 6, 7, 2, 3, 4, 5]` и пишет уставку (`×10`, 0.1 мА) в
`0xD000A3D8 + 8·i`, откуда её берёт `0x800DEBA8 → 0x800DDF88` (запись `0xD0008BB0` поймана write-watch Unicorn:
PC `0x800DE058`, A11 `0x800DEBBE`). Итого исполнитель i = регулятор i (REA `execute_rizin_command`, листинг ASW
Evidence `ev_9c8ca08f…`):

| Регулятор / тип | Pwm ch | Функция |
| :-- | :-- | :-- |
| 0, 1 / тип 0 | 5, 3 | клапаны давления подкоробок N436 / N440 (в работе 0 А = давление пропущено) |
| 2..5 / тип 1 | 0, 7, 6, 2 | клапаны переключателей в порядке вилок прошивки 1/3, 2/4, 5/7, R/6 (N433, N437, N434, N438) |
| 6, 7 / тип 2 | 1, 4 | клапаны сцеплений K1 / K2 (N435 / N439); уставка тока — `0xD0007EE8/EA` с подстановкой (`0x80071AA8`) |

Третий проход ошибочно поменял местами 2/4 и N440 (ch 3 ↔ ch 7): регулятор позиции вилки 2/4 (ток ~0.4–0.9 А)
тогда стравливал подкоробку 2 до ~6 бар, а команда клапана давления подкоробки 2 (0 А) шла на клапан 2/4. После
исправления давление обеих подкоробок = давлению системы, вилки держатся в нейтрали, K2 двигается как K1
(`VERIFIED-T`, `dq200_bench_scenario`). `tcu_dq200::VALVE_PWM_CHANNEL_OF_SOLENOID` = `[0, 6, 1, 5, 7, 2, 4, 3]`
(порядок N433..N440). Характеристики клапанов (ток → давление/расход) — `UNVERIFIED` (у N435/N439 порог
давления — §6.1).

### 4.1 Драйвер мотора на SSC0 / CS P3.6 (`VERIFIED-S`)
- Кадры: 16 бит, **LSB first** (конфигурация каналов Spi `0x8013C4F4`: каналы 0..3 = `0x0F` → CON.BM = 15,
  HB = 0; задания 0..3 `0x8013B90C`: BR = 14 → 2 МГц, PH = PO = 0). Цикл (`0x800D94E2`, 4 задания подряд):
  рег.3 = слово | 3, рег.6 = слово | 6, рег.2 = (слово | 2) & !4, затем запрос статуса `0`/`1` (`0x800D931A`).
  Стартовые слова `0x001F 0x0506 0x1032 0x0001` (`0x8013ABFC`).
- Ответ на кадр N приходит в кадре N+1 (`0x800D93BE`): эхо регистров проверяется по битам 15:2 (рег.3), 15:4
  (рег.6), 15:3 (рег.2); ответ `0x7FFF` → ошибка 4, ответ, равный первому ненулевому слову статуса, → ошибка 2
  (признак перезапуска микросхемы); каждые 10 мс прошивка пишет прочитанные слова обратно.
- Слово статуса (`0x800D95D0`): группы `0x254`/`0x4A8`/`0x902`, биты 0, 12..15 считаются неисправностями
  (счётчики `0xD00082E8..F7`); маска ожидаемых битов зависит от рег.2/рег.3. Модель отвечает 0 (нет
  неисправностей) — смысл битов не установлен.
- Рег.3 бит 14 = фаза измерения нуля усилителя тока (`0x800D9C12`/`0x800D9CC8`: при бите 14 = 1 среднее FADC
  канала 0 → `0xD0008306`, при 0 → `0xD0008304`; ток `0xD0008324` [мА] = (m304 − m306)·10·(3300·1000/500)/(2·1023),
  конфиг `0x8013ABE0`) → 0.0999 В/А на FAIN0P, ток звена постоянного тока (`0xD000B2F8` = /10, ед. 10 мА;
  `0xD000B2FA` = ток/скважность). Пороги перегрузки 30/40 А (`0xD000B2F8`) и 60/80 (`0xD000B2FA`),
  CAL `0x80031E98 + 0x74..0x7E` (`0x800EFD38`).
- Выводы P5 (таблица `0x8013ABC0`): **P5.3** — разрешение моста (`0x800DA228` ставит, `0x800DA24E` снимает),
  **P5.9** — вход коммутации: прерывание шага LTCA2 LTC23 (`0x800DB5FE`, узел 5, SRPN `0x2B`) переключает его
  ровно один раз на шаг (`0x800DB0BC`); P5.4 ставится при инициализации, P5.5/P5.10 пишутся пуском/остановом
  (смысл не установлен, не моделируются).
- Микросхема **не опознана**: ни одна публичная микросхема с таким набором (16-бит SPI LSB first с эхо через
  кадр, вход шага коммутации по фронту, выход нуля ЭДС, усилитель тока с фазой нуля по SPI) не найдена.
  Infineon TLE7183F (data sheet Rev 2.2) — без SPI и без логики коммутации (входы IH1..3/IL1..3); TI DRV3204E,
  onsemi LV8907, Elmos E523.xx — другая архитектура. Поведение моста взято обобщённым по app notes датчиковой
  и бездатчиковой шестишаговой коммутации (Microchip AN970, ST AN1946): каждый фронт входа коммутации
  переключает мост на 60° эл., компаратор плавающей фазы даёт один фронт на шаг (`UNVERIFIED`).

### 4.2 Сигнал IN47 = ноль ЭДС плавающей фазы (`VERIFIED-S` по логике прошивки)
- GPTA0 GTC12 захватывает GT1 по обоим фронтам IN47 (CTR `0x430`, `0x800DA1A0`), ISR `0x800DB7E0` (через
  `0x800E42BC(0, 12)`).
- Прерывание шага проверяет, что с прошлого шага был новый захват и он лежит в окне 40..98 % интервала шага
  (до синхронизации) / 35..65 % (после), окна — `0xD0008378..0xD000837E`; 2 хороших шага подряд → вращение
  обнаружено (`0xD000832B`) → замкнутый контур (состояние 6); 15 неудач → обрыв (`0xD0008383`).
- В замкнутом контуре ISR захвата ставит следующий шаг через половину интервала между двумя нулями
  (LTC23 XR = dt, LTC22 = dt/2, dt = `t_cap − t_cap_prev`) — классическая коммутация через 30° после нуля.
  Отсюда: IN47 — выход компаратора ЭДС плавающей фазы, один фронт на шаг 60° эл. в середине шага.
- Мотор: 4 пары полюсов (`0x8013AC04[0]`: период шага = f·60/(4·6·об/мин)); ШИМ 20 кГц (LTCA2 LTC26..30,
  выход моста = LTC30, `0x800DA96C`); пуск: выравнивание 5 циклов по 10 мс со скважностью `0xD0008348`→`834A`
  (шаг коммутации посередине), разгон 7 шагов по таблице `0x80031D60` (240 → 400 об/мин), удержание 400 об/мин
  до синхронизации; скважности пуска адаптируются двусторонним поиском (`0x800EF568`, `0xD000B3CE/B3EE`).
- Отключение «не набирает обороты» (`0x800EFD38`): при скважности 100 % и отставании от уставки
  (`0xD000A6B2`, 2440..2620 об/мин) больше 500 об/мин насос выключается (`0xD000B37E` = 8).

### 4.3 Модель (`tc1784_io::pump::BldcPump`)
- Мост + мотор + вал: состояние моста 0..5 (A+B−, A+C−, B+C−, B+A−, C+A−, C+B−), ток пары с L/R
  (точное решение на шаге ≤ 25 мкс, ШИМ усреднена по скважности LTC30), ЭДС линейная ke·ω·cos(θ−θc), момент
  ke·i·cos, инерция, кулоново трение, момент шестерённого насоса D·p/(2π η) + вязкий; компаратор — знак ЭДС

### 5.1 Внешнее устройство SSC1 / CS P2.8 = контроль силовых каскадов (`tc1784_io::MonitorDevice`)

Микросхема не опознана (нет даташита); поведение выведено из драйвера и проверок прошивки (REA Evidence
`ev_e6b8bdbb…`, локальный rizin). Регистры (данные — биты 29:6 кадра):
- Идентификация (`VERIFIED-S`, `0x80042010` против констант `0x800460E0`): MCU пишет `0xF60D07` в регистры 15
  и 19 и сравнивает чтение с `0xF60D07`; регистр 14 — командный (ключевые однобитные команды `0x6D7502` при
  старте, `0xA1FE01`, `0xA2FD02`, `0xA3FB04`, `0xA4F708`, `0xA57F10` — `0x800DC5A8`); при чтении прошивка
  требует бит 2 = 1 (`0x800DD7D2`), а записанное значение имеет бит 2 = 0 → чтение = записанное | 4
  (`UNVERIFIED` смысл бита). Без этого — ошибка 9 и программный сброс (так было с эхо-моделью).
- Регистр 8 (читается при старте): биты 5:4 = 10b — иначе ошибка 2 на шаге 9 теста (`0x800428EA`). В модели
  константа `0x20` (`UNVERIFIED`).
- Два канала сторожа «вопрос-ответ» (`VERIFIED-S`): статус — регистры 17 / 20 (читаются каждый цикл, разбор
  `0x800DD610`: биты 11:8 вопрос, 7:4 счётчик ошибок, 3:1, 12, бит 0 = канал в норме), ответ — регистры 18 / 21
  = `table[вопрос]`, таблица `0x80046188` = `0E 0A 06 02 0F 0B 07 03 0C 08 04 00 0D 09 05 01`. Прошивка следит,
  что вопрос меняется и все 16 вопросов встречаются (`0x8004354A`, `0x80043604`), в режиме вынужденного отказа
  шлёт неверные ответы, пока счётчик ошибок < 7 (`0x80043894`); при `(рег17|рег20) & 0xE ≠ 0` шлёт команду
  `0xA3FB04` (`0x8004270A`).
- Тест пути отключения (группа 6, шаги трассируются в `0xD0008590`, функции `0x800428C2..0x80042E40`): по одному
  неверному ответу на канал (`0x8004342A`), измерение ADC[30]/ADC[31] против 0.8·KL30 (`0x80044838`: 0 = оба
  питания есть, `0x55555555` = оба нет, `0x7FFFFFFF` = разные → ошибка): канал 0 неверно → бит 0 канала 0 = 0,
  питания нет; канал 0 верно + канал 1 неверно → бит 0 канала 0 = 1, питание ЕСТЬ; оба верно, затем канал 1
  неверно → бит 0 канала 1 = 0, питания нет; канал 0 неверно + канал 1 верно → бит 0 канала 1 = 1, питание есть.
  Простейшее правило, дающее все четыре исхода и порог прошивки 7: счётчик ошибок канала после включения 8,
  +2 за неверный, −1 за верный ответ, питание отключено, пока хотя бы один счётчик ≥ 7; бит 0 = последний ответ
  верен; вопрос сменяется после верного ответа (по кругу 0..15). Начальное значение, шаги и порядок вопросов
  подогнаны под эти ожидания — `UNVERIFIED` (закреплено тестом
  `tc1784_io::tests::monitor_device_meets_the_firmware_shutoff_path_test`).
- Входы ключа от MCU (`VERIFIED-S`): разрешение P3.9 = 1 / P3.10 = 0 (`0x80043AD2` → `0x800447B8`), запрет
  P3.9 = 0 / P3.10 = 1 (`0x80043AA8`, `0x80043B3E` → `0x800447CA`); собственный вывод разрешения питания
  **P1.13** (тест группы 1 `0x80045972`: сброс P1.13 `0x800459BE` → ожидание «оба питания нет», установка
  `0x80045A30` → «оба есть», иначе ошибка 0x1C). Модель: ключ замкнут ⇔ P3.9 = 1, P3.10 = 0, P1.13 = 1 и оба
  счётчика < 7. Принадлежность входов P3.9/P3.10/P1.13 именно этой микросхеме или отдельному ключу — `UNVERIFIED`.
- От ключа питаются катушки клапанов (`Tc1784Io::valve_supply_v`) и входы ADC[30]/ADC[31] (`valve_supply_pin_v`,
  подставляются в момент преобразования). Устройство подключено по умолчанию (`MonitorDevice::attached`).
- Результат (`VERIFIED-T`, `dq200_watch`, native и Unicorn): драйвер в состоянии 0x22, слово безопасности
  `0x55555555` с 12 мс, тест группы 6 до шага 0x35 и тест группы 1 проходят, ошибок 0, сбросов 0.

### 5.2 FADC (`tc1784_io::fadc`, TC1796 UM гл. 26)

- Ядро FADC TC1784 по адресу `0xF0100400` с раскладкой регистров TC1796 (TC1796: `0xF0100300`, UM Табл. 18-28):
  драйвер `0x800E2AB0` пишет CLC, FDR `0x8012`, GCR `0x00200000` (ANON), ACR0/ACR1 = 5 (однопроводный
  FAINxP − VFAREF/2, усиление 2), CFGR0 = `0x00AF1445` (таймер канала, fCT = fFADC, CTREL 0xAF), CFGR1 =
  `0x90010045` (IEN, SR1), NCTR = 2 (запуск канала 1 соседом 0), SRC1 = SRPN 0x23; `0x800ED498` выключает
  каналы 2/3 (ACR2/3 ENP = ENN = 0); фильтры (FCRn) не пишутся (`VERIFIED-T`, трасса `DQ_TRACE=F0100400,F01004FF`;
  REA `ev_f3b3cd1c…`).
- Тактирование: fFADC = fFPI·18/1024 = 1.0547 МГц (UM ур. 26.4); период таймера канала (CTREL + 1) = 176 тактов
  → 166.9 мкс (5.99 кГц, совпадает с 6-кГц запуском АЦП GPTA); преобразование 21 такт = 19.9 мкс (ур. 26.2).
- ISR SR1 (`0x800E40E8` → `0x800ED4E0`, REA `ev_f5e896e4…`): RCH0 → ADC[32], RCH1 → ADC[34]; ADC[32] →
  накопитель тока насоса `0x800D9BBE` (§4); ADC[34] → проверка 7 ПО безопасности (окно 764..1023, замена `0x37D`).
- VFAREF = 3.3 В: в TC1796 (UM 26.1, Табл. 26-1); прошивка сама пересчитывает отсчёты FADC с 3300 мВ / 1023
  (`0x8013ABE0`) — допущение о TC1784 `UNVERIFIED` по даташиту, но согласовано с прошивкой.
- Вход FAIN1P (проверка 7) — шина платы неизвестного назначения, подаётся номинал прошивки `0x37D` → 2.88 В
  (`tc1784_io::FADC_RAIL_CH1_V`, `UNVERIFIED`), как ADC[21]/[12]/[16]. FAIN0P — ток насоса (сейчас 0).
- Модель событийная: время следующего события (срабатывание таймера канала / конец преобразования) отдаётся в
  `tc1784_insns_to_next_event`, без опроса по инструкциям. Не моделируются (прошивка не использует): фильтры,
  внешние триггеры TS[7:0], входы стробирования GS[7:0], калибровка, динамический приоритет, запросы DMA.
- Тесты: `tc1784_io::fadc::tests::dq200_configuration_converts_ch0_ch1_at_6khz_and_raises_sr1` (период 176 тактов,
  первый SR1 через 176 + 2·21 такта, коды по Табл. 26-1), `input_stage_matches_um_table_26_1`.

### 5.3 Надзор ПО безопасности за задачами и расхождение Unicorn/native (четвёртый проход)

Надзор (`VERIFIED-S`, функции `0x80041A28` (+1 к счётчику), `0x80041B12`, `0x80041C2C`, `0x80041D78`; таблица
`0x8004610C` → записи по 6 байт: минимум, допуск, число вызовов проверки, порог ошибок; счётчики `0xD00084A0 +
0x20·i`):

| i | что считает | окно | норма |
| :-- | :-- | :-- | :-- |
| 0 | время между вызовами 10-мс задачи `0x800EBBA8` по STM (единица 100 мкс, `0x80041B12`) | каждый вызов | 90..110 |
| 1 | уведомление периода Pwm ch 0 = 3-кГц токовые регуляторы (`0x800EB430`) | 4 проверки | 116..124 |
| 2 | 2-мс уведомление таймера `0x800EB630` | 4 | 19..21 |
| 3 / 4 / 5 | задачи ОС `0x800EBFB0` / `0x800EC178` / `0x800EC3E0` (таблица задач `0x8013B07C`) | 20 / 20 / 24 | 9..11 / 4..6 / 2..4 |

Проверка элемента 0 (`0x80041DE8..0x80041E1C`) сравнивает d15 = период − 90 (единицы 100 мкс) с допуском 20:
обычно 9..13 (период 9.9..10.3 мс), «21» = период 11.1 мс, период < 9.0 мс даёт d15 = −1 (беззнаково — тоже
ошибка). Выход за окно хотя бы раз (порог ошибок 1) → ошибка `0x17` (`0x80041D4E`/`0x80041E4C`, номер элемента и счёт —
`0xD001FF64`/`0xD001FF60`) → `0x80044326` → программный сброс `0x800453CC` → `Mcu_PerformReset 0x800E4C4C`
(SWRST, PC `0x800E4C84`). Маска ошибок в неинициализируемой RAM `0xD001FF70` сохраняет бит 23 (`1 << 0x17`), после
перезапуска тест пути отключения даёт ошибку 2; вес — 10 на сброс (`0xD001FF7C`), при 22 отключение фиксируется.
Это и был «бит 23» прежнего описания (`VERIFIED-T`: пробы `0x800E4C4C` (A11 = `0x800453D8`, D8 = `0x17`),
`0x80044326`, наблюдение `0xD001FF60..84`).

Причина расхождения бэкендов (`VERIFIED-T`):
1. Unicorn доставлял прерывание, ставшее возможным после ENABLE / RESTORE / RFE / MTCR ICR / BISR, только в конце
   кванта (до `QUANTUM_MAX_INSNS` = 2000 инструкций = 16.7 мкс при 120 МГц); нативное ядро заканчивает квант сразу
   (`IrqCheck`), как CPU (V1 §5.3). Порядок вытеснения задач различался, период 10-мс задачи на Unicorn гулял 90..107
   (native 99/100) и на ≈4.87 с упал до 89 → ошибка 0x17 (элемент 0). Эксперимент: native без остановки по
   `IrqCheck` даёт тот же сброс уже на 1.235 с. Исправление: `isa_fix::irq_site` — хук на этих инструкциях
   заканчивает квант Unicorn после инструкции, если запрос выигрывает (`Tc1791HardwareState::irq_wins`, общий с
   native); тест `isa_fix::tests::interrupt_taken_right_after_unmasking` (оба бэкенда; без хука падает).
2. Запросы GPTA (периоды Pwm, шаг коммутации V401, таймерные каналы) доставлялись на ближайшей границе кванта, а
   границы у бэкендов разные; на Unicorn (шаг co-sim 5 мс) 2-мс уведомление (элемент 2) один раз насчитало 12 вместо
   19..21 → сброс на 3.325 с. Исправление: квант режется на следующем внутреннем событии GPTA
   (`Gpta::next_event_tick`, `tc1784_io::gpta_insns_to_next_event`; тест `gpta_next_event_is_the_request_tick`).
   После обоих исправлений: период 10-мс задачи на Unicorn 99/100 (как native), Unicorn 8 с при шаге 5 мс и 16 с при
   шаге 100 мс — без сбросов.
3. Остаток: Unicorn исполняет блоки трансляции целиком (первый блок кванта может перешагнуть событие на длину
   блока), фронты IN47 (нуль ЭДС V401) поднимают захват на границе кванта; счётчики ISR насоса за 3.3 с: 2028/4052
   (Unicorn) против 2148/4314 (native) — бит-в-бит совпадения нет, поведение совпадает. Record/replay
   (`board_replay`, 150 М инструкций DQ200) — 0 расхождений: дефекта транслятора на этом участке нет.

### 6.1 Сцепления: датчики хода, монитор P0810, клапаны (четвёртый проход)

- Характеристика датчиков хода (`VERIFIED-S`): `0x80135A58` (копия в PSPR `0xD40019B0`) переводит скважность каждого
  канала Icu (0.01 %) двухточечной линией из CAL `[0xD000C4A8]` = `0x80031F4C`: канал A 1000 → 0, 9000 → 2900;
  канал B 1000 → 2900, 9000 → 0 (в `0xD000C4AC`). Ход сцепления `0xD0007E68`/`6A` = среднее двух каналов
  (`0x80136736`; 3000 при недостоверности). Единица 0.01 мм — `HYP` (29.00 мм на 10..90 %). Прежняя модель платы
  давала 17 мм на 10..90 % → прошивка видела ход ×1.7. Теперь `tcu_dq200::clutch_travel_duty` — обратная к этой
  линии (тест `clutch_sensor_duty_inverts_the_firmware_characteristic`).
- Адаптации (EEPROM, зеркало `0xD0003ECC`/`0xD0003F00`, по 3 полуслова): K1 145 / 775 / 2435, K2 184 / 836 / 2500.
  Первое значение входит в нижнюю границу окна P0810 (+300), второе внутри окна → `HYP`: 7.75 / 8.36 мм — точки
  касания K1/K2; смысл первого и третьего не установлен. Точки касания plant (`DryClutchHw::kiss_mm`) взяты из них.
- Монитор P0810 (`0x80085E82`, события из `0x80138650`: K1 `0x74`/`0x3E`, K2 `0x75`/`0x3F`, `VERIFIED-S`):
  измерение h = история `0xD0007E68` (5 отсчётов по 10 мс), ожидание g = PT1 от `0xD0006092`/`9A` (`0x800BD1F0`);
  проверка идёт, пока h или g в окне [T1, T2] = [`0xD0005F12`, `0xD0005F16`] (4.45 / 11.59 мм на стенде;
  T1 = max(`0x80092370`, адаптация₁ + CAL 300)); если все 5 отсчётов отличаются от g больше допусков и h ≥ g →
  счётчик `0xD0005F1C` → P0810 через 10 циклов, при h < g — событие `0x3E/0x3F`. Реакции событий (`0xD000CC0C` +
  0x2BC + 2·событие): P0810 K1 `0x400F` (бит 3 → `0xD0004D0E`), K2 `0x8017` (бит 4 → `0xD0004D0F`) — отключение
  подкоробки (`0x8006AEF2..`).
- Что делает прошивка в состоянии 4 (`VERIFIED-T`): g = 0 (сцепления разомкнуты), а клапаны сцеплений ведутся
  током удержания: требование `0xD000A408`/`A410` нарастает от 0.168 А шагами 22 мА/10 мс и стоит на 0.533 /
  0.544 А. Значит, при таком токе реальный клапан не создаёт давления, сдвигающего поршень за 4.45 мм.
- Plant: (1) золотник клапана следует за током катушки модели платы (`TcuOutputs::solenoid_current_a` ←
  `CoilLoad::i_mean_a`, точный интеграл R-L за 1 мс), а не за оценкой по декодированной скважности (та давала
  ~0.7 А при регулируемых прошивкой 0.53 А); (2) порог давления клапанов сцеплений `clutch_valve_threshold` =
  0.65 А (`UNVERIFIED`, ограничен снизу поведением прошивки: при 0.08 и 0.6 сцепление K2 доходило до 6.96 мм и
  срабатывал P0810, при 0.65 оба остаются разомкнутыми, P0810 нет). Альтернатива, не исключённая: клапаны
  N435/N439 — расходные 3/3 с нулём около 0.53 А (Actronics называет их клапанами давления).
- Затяжка разомкнутого сухого сцепления: был постоянный момент 0.25 Н·м на ступицу → первичные валы в нейтрали
  раскручивались до оборотов двигателя. Теперь только воздушный зазор, 2·10⁻⁵ Н·м·с/рад (`open_drag_nm_s`,
  `UNVERIFIED`; разжатые диски не касаются, подшипник выключения тормозит ведущую сторону, а не ступицу); валы
  стоят (G501/G502 = 0 при работающем двигателе, `VERIFIED-T`).

SPI: SSC0 CS P3.5 — EEPROM; SSC0 CS P3.6 — 16-бит кадры `0x001F 0x0506 0x1032 0x0001` с частотой ~3 кГц;
SSC0 CS P3.7 / P2.13 — 16-бит кадры (`7/0x3800`, `6/0x2800`, `0x10/0x1840`); SSC1 без CS — `0x3F`; SSC1 CS
P2.8 — 32-бит устройство §5. Все, кроме EEPROM, не опознаны (MRST = все единицы).

## 8. Блокеры и следующий шаг

Четвёртый проход (2026-11-02):
- Причина «4 → 5 не идёт» третьего прохода разобрана: `0xD0007E1B` = 5 в нейтрали — норма (§7); 3 бывает только
  с включённой передачей. Передачи не включались, потому что через ~0.5 с после входа в состояние 4 срабатывал
  P0810 на обоих сцеплениях (сцепления закрывались при токе удержания 0.53 А, §6.1) → реакции отключали обе
  подкоробки (`0x4D0E/0F` = 1) → путь `0x5DC` модуля правдоподобия (всегда 5), цели передач сброшены. Плюс
  перепутанные 2/4 ↔ N440 (§3.1) стравливали подкоробку 2.
- Исправлено: назначение клапанов (§3.1), характеристика датчиков хода (§6.1), ток золотника из модели платы,

  `0x7E1B` = 1 (таймаут `0x7DC8`) и цели 7 / 6.

  перезаряжается (CAL `+0x5F`), пока обратный счётчик `0xD0006F40` ≠ 0; `0xD0006F40` (`0x800BE9xx`) отсчитывает

## 9. Plant (`simemu-physics`) против DQ200

- 8 клапанов, 2 подкоробки по 4 (два клапана вилок, клапан сцепления, клапан давления подкоробки) — согласуется с
  группировкой прошивки (§3) и описанием [Actronics, TCU DSG7 DQ200](https://www.actronics.co.uk/news/tcu-dsg7-dq200).
- Ток клапанов до ~1 А (уставки 0.97–0.99 А, потолок регулятора 1.6 А) согласуется с `SolenoidHw::TYPICAL`
  (5 Ом, 12 мГн, 1 А — `UNVERIFIED`); ШИМ 3 кГц (`VERIFIED-S`).
- Аккумулятор: предзаряд 20 бар (`UNVERIFIED`) ниже порогов «давление достаточно» прошивки (21–33 бар,
  §7) — согласовано; рабочий диапазон 40–60 бар по Actronics. Насос работает прерывисто по порогу давления
  ([skodabook, 0AM](https://www.skodabook.ru/en/Superb/B6/transmission/dsg-0am/obschaya-informaciya-o-7-stupenchatoy-transmissii-dsg-oam)).
- Сухие сцепления нормально разомкнуты, рычаг + подушечная пружина, точка касания смещается от износа и
  температуры (источники в `clutch.rs`: Naunheimer et al. 2011; Myklebust 2014/2015; Archard 1953; Bijwe
  1997). SSP 390 в этой сессии недоступен — данные о V401/аккумуляторе из него не сверены.
- Отказы из физики (задача 4, проверено чтением кода и тестами физики): износ накладок ∝ энергии трения
  (Archard) с ускорением выше 200 °C, остекловывание/выгорание по температуре, работа синхронизаторов и
  удар зубьев муфты по энергии и износу кольца, усталость шестерён/валов по Miner (`driveline_failure.rs`);
  тесты `dq200_launch_abuse_fades_and_burns_the_clutch`, `dq200_synchroniser_work_and_dog_clash_with_worn_ring`.

- Третий проход: подача насоса — от вала V401 модели платы (`DcPump::driven`, 0.6 см³/об, `UNVERIFIED`);
  полоса аккумулятора, которую держит прошивка на стенде, ≈ 42..58 бар (совпадает с 40..60 бар Actronics).
  Геометрия вилок — по адаптациям EEPROM (синхронизатор 2.8, упор зубьев 4.3, включено 6.5, полное 8.8, упор 9.8 мм;
  разбиение между синхронизатором и полным включением `UNVERIFIED`), вилка 3 = R(+)/6(−). Клапаны давления
  подкоробок — падающая характеристика. Четвёртый проход: затяжка разомкнутого сухого сцепления — только воздушный
  зазор (§6.1), первичные валы в нейтрали стоят; точки касания 7.75 / 8.36 мм из адаптаций; клапаны сцеплений —
  порог 0.65 А; ток золотников — из модели катушек платы (`TcuOutputs::solenoid_current_a`).
- Литература, сверенная в этом проходе: VW Workshop Manual «7-Speed Dual Clutch Transmission 0AM», Edition 09.2015
  (сухие многодисковые сцепления с поочерёдным гидравлическим включением через рычаги включения, без педали;
  passatworld.ru/othr/b7/7dual_clutch.pdf); Actronics «TCU DSG7 DQ200» (N435/N439 — клапаны давления сцеплений
  K1/K2, N436/N440 — давления подкоробок, питают свои N433/N434/N435 и N437/N438/N439; 40..60 бар). SSP 390 и
  статьи LuK в этой сессии в машиночитаемом виде не получены — данные о характеристиках клапанов и ходах из них не
  сверены.

## 10. Реальное время (native, текущая macOS)

- Плата DQ200 одна (`perf_determinism`, 5 с, native, машина под нагрузкой других задач, load avg ≈ 9):
  подряд «до» (бинарник основного дерева) 80–81 MIPS, RTF 0.67–0.68; «после» 80–88 MIPS, RTF 0.67–0.73 — разницы
  нет. При fCPU 120 МГц прошивка исполняет ~119.5 М инструкций/с без простоя, поэтому требование 1:1 для платы ТКУ
  сейчас не выполняется — это ограничение ядра (MIPS), а не моделей. Дайджест ТКУ изменился
  (`7a28bf82e4b812ce` → `d6b4b8ff718bde15` native, Unicorn 3 с: `6007fa28716f6ffe`) — из-за датчиков тока
  катушек, обратного чтения P2.1 и шин §5 (прерываний ADC/ISR меньше: 147480 → 144028 за 5 с).
- Модель катушек: 2.2 нс на обновление, ~110 тыс. обновлений/с → 0.024 % реального времени
  (`tc1784_io::tests::coil_load_cost`); без выделений памяти в горячем цикле.
- Studio (ЭБУ + ТКУ в своём потоке + plant): сценарий `dq200_bench_scenario` 16 с за 23.3 с вместе с

### 11.2 Драйверы клапанов на SSC0 и разрешение переключений (`VERIFIED-S/T`)

## 14. Восьмой проход (2026-11-04): «сцепления постоянно буксуют» — модель сцепления прошивки против plant

пробы только чтением DSPR (`SIMEMU_TCU_WATCH`, `drive_run::tests::dq200_slip_scenario`). Код и RAM прошивки не менялись.

### 14.1 Как прошивка задаёт сцепление (`VERIFIED-S`)
- Запрос момента сцепления `0xD0006020[s]` (0.1 Нм, ограничен −200 Нм .. `0xD0006058`) → `0x800921E6` → ход
  `0x80092370(T, s)` = `0x800923AA` (масштаб трения: T·1024/`0xD0006080[s]`·CAL`[0xD000CC84]+0x5C8`/1024; `0x6080` = 1023–1064 в
  езде) → `0x800505C0` (T·10000/`0xD00038DA` = 10000 → характеристика `0x80055EFA` или таблица `0xD00036CC`/`0xD0003708`,
  15 точек) → `0x800924AC` (+ CAL +0x5C4 = 0 + адаптация точки касания `0xD0006088` = 0, предел `0x800BD1BA`) →
  `0x80093B1C` → `0xD0006090 + 8s` (+0 цель, +2 цель после подмены `0xD000359C` (`0x8009360C`), +4 фильтр измеренного хода
  `0x800931D8`, +6 ток регулятора).
- Характеристика `0x80055EFA` (поплавковая): для T между 0 и 669/700 Нм ход = кисс + u, где
  T(u) = a0·(u + √((u − a4)² + a2) − √(a4² + a2)); параметры в RAM `0xD000399C + 0x14·s` (a0, кисс, a2, a3 = 0, a4):
  K1 31.675 / 4.86 / 58.645 / 0 / 3.8788, K2 49.105 / 7.87 / 18.8915 / 0 / 8.1231 (`VERIFIED-T`). Они подогнаны к четырём
  опорным точкам из эталонном EEPROM **0x880..0x8BF** (ход 0.0001 мм, момент 0.01 Нм; копия 0x8C8): K1 4.86 / 6.75 / 13.33 /
  20.52 мм при 0 / 39.2 / 279.2 / 669.2 Нм, K2 7.87 / 11.98 / 20.20 / 23.05 мм при 0 / 37.5 / 450.1 / 700 Нм — кривая проходит
  через точки (K2 11.98 мм: 39.9 Нм). Умолчание CAL (0x80020040: K1 кисс 8.50, K2 6.30 мм) не используется — адаптация
  загружена. Проверка: цель K2 1587 при запросе 155.2 Нм = табличное значение 1592.
- Характеристика ход → давление привода, по которой работает контроллер положения `0x80093674`: при флаге `0xD0006197` = 1
  (в езде 1/1) — адаптированные таблицы `0xD00060EC/0xD0006110/0xD0006134` (не номинал CAL 0x800312CC/0x80031284), из EEPROM
  **0xB2C..0xB8B** (копия 0xB90; ось — 8 точек до упора 0xAC0 K1 24.35 / K2 25.00 мм, впереди упор открытия 1.45 / 1.84 мм).
  Их пишет базовая установка `0x80060DA4`: клапан сцепления открыт током подмены `0xD00035A0` (`0x80062ADC`), давление
  подкоробки — подменой `0xD00035A4` (`0x80062A78` → `0x80071D68` → `0x80071D1C`, т. е. через таблицу p→I клапанов подкоробок,
  которую plant воспроизводит), шаг 0.20 бар на вызов (CAL `[0xD0004248]` = 0x800204E0 +0x24E/+0x24A); «отпускание» `y1` —
  давление, при котором ход падает на 0.40 мм ниже точки (+0x274), «прижатие» `y2` — давление, при котором ход в пределах
  0.30 мм от точки (+0x294). K1 `y1` 5.4 5.4 4.8 4.6 6.0 10.8 18.2 27.4 38.8, `y2` 16.0 16.0 17.2 17.8 14.2 18.6 25.8 35.6 45.6
  бар; K2 `y1` 4.8 4.8 5.6 6.6 8.2 11.6 17.6 27.2 39.0, `y2` 14.0 14.0 15.0 15.2 16.2 19.2 25.2 35.2 45.6 бар. Кривая K1
  нисходящая, K2 растущая — как в описании LuK двойного сцепления DQ200 (Schaeffler Kolloquium 2010, «Dry double clutch»:
  «the force curve of clutch 1 … has a downward slope … clutch 2 permanently slopes upward»; «actuation … only … by means of
  an actuator with travel control»).
- Клапаны N435/N439 — пропорциональные распределители расхода, не клапаны давления: ток регулятора сцепления
  (`0x80094CE4`, запись `0xD0006250`) = CAL `[0xD000CC88]`(= 0x80031584) +0xFA = 0.53 А + карта(P-запрос) + интегральные
  члены; P-запрос `0xD0006234` = ошибка хода (0.01 мм) · Kp/1000, Kp = 10·√(10⁷/Δp) с ограничением 800..1200 ‰
  (`0x800953A0..0x80095484`: целочисленный √ — компенсация расхода через кромку ∝ √Δp); карта CAL +0x86 (запрос −650..770) →
  +0xB2 (ток −0.53..+0.47 А) перескакивает ±19–20 мА у нуля — компенсация перекрытия золотника. 0.53 А — ток, который
  прошивка держит в P/N. SSP 390: N435/N439 «управляют объёмом масла». Прежняя модель plant (давление 250 бар/А выше
  0.60 А) этому не соответствует.
- Ожидаемая динамика хода (монитор P0810 `0x80085E82`): PT1 цели `0x800BD1F0` с α = коэффициент/10000 на вызов; при 0 °C
  (G510 не найден, прошивка читает 0 °C) α = 0.32 → τ ≈ 26 мс.

### 14.2 Причина (`VERIFIED-T`, `dq200_slip_scenario`, база `863a585`, native)
1. Plant давал на ходе, который прошивка ставит под запрошенный момент, намного меньше момента: K1 ≈ ⅓ (13.47 мм: 88 Нм
   против 286 Нм модели прошивки; кисс plant 7.75 мм против 4.86), K2 на 75–90 % выше 15 мм (кисс 8.36 против 7.87).
   Прежняя «подгонка» (`DryClutchHw::dq200`, F ≈ 1.9 кН·x²) была сделана по целям хода, которые прошивка уже накрутила
   регулятором проскальзывания, — замкнутый круг. Итог: K1 трогает с проскальзыванием 700–1400 об/мин, в 3-й запрос
   294 Нм при 76 Нм двигателя (ёмкость 75 Нм), p95 проскальзывания 118 об/мин.
2. Клапан сцепления моделировался клапаном давления с трением 80 Н: контроллер положения прошивки (расходный P-регулятор
   вокруг 0.53 А) раскачивал ход ±1.5 мм с 25 Гц (давление 1.5 ↔ 30 бар), сцепление в 4-й проскальзывало при каждом
   провале хода (p95 129 об/мин), расход сцеплений съедал подачу V401: давление системы до 35.8 бар (условие P0841 —
   36.0 бар, запас −0.21 бар).

### 14.3 Изменения plant (одна модель по спецификации выше)
- `clutch::DryClutchHw::dq200`: кисс 4.86 / 7.87 мм; момент на ходе = T(u) прошивки (`torque_curve`), прижим = T/(2·μ·r)
  (μ-фейд, остекловывание, износ, коробление действуют как прежде); сила на приводе — среднее `y1`/`y2`
  (`actuator_bar`), кулоново трение — половина разности (`ClutchHw::actuator_friction_n`). Удалены подушка/жёсткость/
  возвратные пружины прежней подгонки.
- `mechatronic::Dq200HydraulicsHw`: N435/N439 — распределители 3/3 (`Feed::Valve` от давления подкоробки к баку),
  нейтраль 0.53 А, открытие по карте прошивки (обратная, запрос/770), кромка k = 9.2·10⁻⁸ м³/(с·√Па) (≈ 3.2 мм²; из
  Kp·√Δp = 10⁶ и τ = 26 мс: k = 7.7·A/(τ·10⁶), `UNVERIFIED`), вязкое демпфирование привода 100 Н·с/м (было 2000;
  ≤ 270 по таблице базовой установки: K2 дошёл до 7.62 мм всего на 1 бар выше начала плоского участка при рампе 20 бар/с).
  Прежние `clutch_valve_gain/threshold`, `pressure_valve_*`, `clutch_friction_n` удалены.
- `HYP`: что опорные точки и кривые EEPROM описывают физические сцепления эталонного автомобиля (их выучил ТКУ на машине);
  что гистерезис `y2 − y1` — кулоново трение; что карта +0x86/+0xB2 линеаризует клапан (запрос ∝ расход).

### 14.5 Девятый проход (2026-11-08): интегратор и перекрытие золотника `0x80094CE4..0x80095C86` (`VERIFIED-S`)
- Полный статический разбор 2-мс (`500 Гц`) регулятора положения сцеплений `0x80094CE4..0x80095C86` через REA
  (`ev_d688f9746ea45d35a6c2e39d0c6872fa84d5056fa13cfd10b8b6d4ba49eba865`,
  `ev_1280258774570ac984c25c7094cde118e5a4a1e6da15b6c1c0a66a140c3f0dc1`,
  `ev_e2e679c6412edcb3015925dd79a2ba10ca667a127de536f01cd8f306acf651ad`,
  `ev_67e7d88b75fd4ae05be3d5bdabde829e01f8407582125d69768acbc726638b23`,
  `ev_2371bcc366c7198a5549529a5f86f1df16e590af1025a9f87f941cd9e8bf70c0`,
  `ev_7c0047de53d866a49220ea6213362e436638284b324dc9c957a4c3fd0b2b7173`; дескриптор `*(0xD000CC88) = 0x80031584`):
  1. PD-запрос скорости (`0x80095154..0x800952FA`): `err_k` (`0xD0006240 + 2k`, в `0.01 мм`),
     `D_k = 500·(err_k − prev_err_k)·gain_D(|err_k|)/100` (`CAL+0x1A..+0x28`: `[50, 50, 30, 10, 0, 0, 0, 0]` по оси
     `|err_k| = [0, 15, 30, 50, 100, 150, 200, 400]`), `P_k = err_k·gain_P(|err_k|)/100` (`CAL+0x2A..+0x38`:
     `[4000, 4000, 3900, 3700, 2800, 2200, 1600, 1000]` → `Kp = 40 с⁻¹` при `|err_k| ≤ 0.15 мм`),
     `v_PD,k = clamp(P_k + D_k)` (`0xD0006230 + 2k`).
  2. Компенсация перепада на кромке (`0x80095300..0x80095504`): при `v_PD,k ≥ CAL[0xDE](5)` наполнение (`ΔP = P_sys − P_clutch`,

  3. Обращение характеристики клапана (`0x80095598..0x80095814`): таблица `CAL+0x86 → CAL+0xB2` переводит `q_PD,k` в

     `ΔI_total,k = ΔI_PD,k + I_k` складывается в пространстве тока (`0x80095B86`) с нейтралью `CAL[0xEC] = 5300` (`530.0 мА`).
- Причина остаточного предельного цикла на 2-й передаче после слияния (`p95 = 58.3 об/мин` в `dq200_slip_scenario`):
