### 0. Базовые примитивы и константы ПЗУ

* **`AES128(K, Block16)`** — стандартное прямое шифрование одного 16-байтового блока **AES-128** (FIPS-197, режим ECB без сцепления и дополнения; в прошивке `0x0013F66A`, в модели aes).
* **`CRC32(data)`** — стандартный отражённый **IEEE 802.3 CRC-32** (`zlib.crc32`, полином `0xEDB88320`, `init = 0xFFFFFFFF`, `xorout = 0xFFFFFFFF`; в прошивке `0x0013F4D6`, в модели crc32_ieee).
* **`CRC16(data)`** — **CRC-16/CCITT-FALSE** (полином `0x1021`, `init = 0xFFFF`, без отражения, `xorout = 0x0000`, проверка `CRC16(b"123456789") == 0x29B1`; в прошивке `0x0013F4A2`, в скрипте crc16_ccitt).
* **Константы в образе `ac-cflash.bin`** (адрес = смещение в файле):
* `C4` = `cflash[0x19CFF8 : 0x19CFFC]` (4 Б, константа варианта 3, `0x00138256`)
* `c7p` = `cflash[0x19D004 : 0x19D00B]` (7 Б, хвост блока запроса партнёра группы Б)
* `c7a` = `cflash[0x19D00B : 0x19D012]` (7 Б, хвост блока ответа приборки группе Б)
* `c10` = `cflash[0x19D1D8 : 0x19D1E2]` (10 Б, хвост блока `MAC` команды `2E 02E1`)

### 1. Слоты `A, B` (по 16 Б) и производные ключи партнёров `K_n`

#### 1.1. Перестановка `S0, S1 ↔ A, B` (`0x0013FC24`, data_02f7)
В транспондере ключа лежат `AES128(K_c, A)` и `AES128(K_c, B)`, а в пакете привязки `2E 02F7` (и временно в `EEL 0x69`) те же два 16-байтовых секрета передаются перемешанными как `S0, S1` (операция симметрична сама себе):
```python
S0 = A[0:4] + B[4:12] + A[12:16]
S1 = B[0:4] + A[4:12] + B[12:16]

# Обратно в прошивке (0x0013FC24):
A  = S0[0:4] + S1[4:12] + S0[12:16]
B  = S1[0:4] + S0[4:12] + S1[12:16]
```
В `EEL 0x68` (`0xFEDF52EE` и `0xFEDF52F2`) постоянно хранятся `CRC32(A)` и `CRC32(B)` в **Little-Endian** (`<I`).

#### 1.2. Нарезка ключей партнёров `K_n` из `A` и `B` (`0x0013FD6E`, partner_key)
Приборка не хранит отдельные ключи `ECU` и `TCU` — каждый 16-байтовый ключ `K_n` собирается склейкой кусков `A` и `B` (ac-immo-she.md` §3.3):

| Партнёр (группа) | Кадры CAN (запрос → ответ AC) | Индекс `n` | Формула 16-байтового ключа `K_n` |
|---|---|---|---|
| **Партнёр 0** (Б, **ECU** двигателя) | `0x010` → `0x011` | `0` | `A[0:4] ‖ B[4:12] ‖ A[12:16]` |
| **Партнёр 1** (Б, напр. **TCU**) | `0x012` → `0x013` | `1` | `B[0:4] ‖ A[4:7] ‖ B[7:12] ‖ A[12:16]` |
| **Партнёр 2** (Б, напр. **TCU**) | `0x014` → `0x015` | `2` | `B[0:2] ‖ A[2:4] ‖ B[4:12] ‖ A[12:14] ‖ B[14:16]` |
| **Партнёр 3** (Б) | `0x016` → `0x017` | `3` | `A[0:6] ‖ B[6:10] ‖ A[10:16]` |
| **Партнёр 4** (Б) | `0x018` → `0x019` | `4` | `B[0:1] ‖ A[1:4] ‖ B[4:7] ‖ A[7:9] ‖ B[9:12] ‖ A[12:15] ‖ B[15:16]` |
| **Партнёр 5** (А, напр. ELV) | `0x01A` ↔ `0x01B` | `5` | `A[0:16]` |
| **Партнёр 6** (А) | `0x01C` ↔ `0x01D` | `13` | `A[0:4] ‖ B[4:9] ‖ A[9:12] ‖ B[12:16]` |
| **Партнёр 7** (А) | `0x01E` ↔ `0x01F` | `14` | `A[0:2] ‖ B[2:4] ‖ A[4:6] ‖ B[6:10] ‖ A[10:12] ‖ B[12:14] ‖ A[14:16]` |

*(Внутри самих `ECU` и `TCU` хранится уже готовый 16-байтовый `K_n` в слоте аппаратного SHE — знать про `A` и `B` по отдельности им не нужно.)*

### 2. Формула `MAC`, рукопожатия `ECU`/`TCU` и вычисления `ID` при привязке

#### 2.1. Функция 4-байтового `MAC` (`0x00138F5E`, mac)
Пусть `K` — 16-байтовый ключ партнёра (`K0` у ECU, `K1`/`K2` у TCU), `Block16` — 16-байтовый вход, `ID = [ID0, ID1]` — 2-байтный идентификатор отправителя кадра:
```python
C   = AES128(K, Block16)          # 16 байт шифротекста
crc = CRC32(C)                    # uint32

c0 =  crc        & 0xFF           # младший байт CRC-32 первым (Little-Endian!)
c1 = (crc >> 8)  & 0xFF
c2 = (crc >> 16) & 0xFF
c3 = (crc >> 24) & 0xFF

MAC = bytes([c0, c1, c2 ^ ID[0], c3 ^ ID[1]])
```
Первые два байта (`c0, c1`) доказывают знание ключа `K` и байта класса мощности, а старшие два байта (`c2 ^ ID[0], c3 ^ ID[1]`) несут замаскированный 2-байтный `ID` отправителя.

#### 2.2. Запрос `ECU` / `TCU` → приборка (`0x010`, `0x012`, `0x014`, 8 байт)
Ведомый блок генерирует 4-байтовый случайный вызов `P[0..3]`, берёт общий байт конфигурации/класса мощности `cfg` (в приборке `0xFEDF52F6`) и свой 2-байтный `ID_p` (engine_frame):
```python
Block_req = C4 + bytes([cfg]) + P + c7p          # 4 + 1 + 4 + 7 = 16 байт (0x00138DE6)
tx_frame  = P + MAC(K_n, Block_req, ID_p)        # 4 + 4 = 8 байт на CAN
```

#### 2.3. Проверка в приборке и формула обучения `ID_p` (`0x00138F5E` → `0x00138404`)
Приняв 8 байт `rx[0..7]`, приборка берёт `P = rx[0:4]`, строит тот же `Block_req` на своём `K_n` и считает `c0, c1, c2, c3 = CRC32_LE(AES128(K_n, Block_req))` (ac-immo-she.md` §4.3):
1. **Проверка ключа и `cfg`:** должно выполняться `rx[4] == c0` **и** `rx[5] == c1`.
2. **Извлечение `ID` отправителя прямо из кадра:**
   ```python
   ID_cand = bytes([rx[6] ^ c2, rx[7] ^ c3])
   ```
3. **Обычный режим vs обучение партнёра (`0x00138404`):**
   * **В обычной работе:** сверяется `ID_cand == ID_stored` (из `EEL 0x66`: `0xFEDF52A6` у партнёра 0, `0xFEDF52B0` у партнёра 1, `0xFEDF52A8` у партнёра 2).
   * **В режиме обучения партнёра** (в `0xFEDF52B2` поднят бит партнёра): на 1-м кадре с верными `c0, c1` приборка запоминает пару `(P_1, ID_cand_1)` в `0xFEDF53A8 + 8*p`. Когда приходит 2-й кадр с **новым вызовом** `P_2 != P_1`, у которого снова сошлись `c0', c1'` и получилось **`ID_cand_2 == ID_cand_1`**, приборка сохраняет `ID_cand` в `EEL 0x66` и сбрасывает бит обучения этого партнёра.

#### 2.4. Ответ приборки → `ECU` / `TCU` (`0x011`, `0x013`, `0x015`, 8 байт)
Через 20 мс приборка инвертирует все биты вызова `P` (`~P`), подставляет `c7a` и свой собственный 2-байтный `ID_ac` (`0xFEDF52A4`, engine_expected_answer):
```python
not_P     = bytes([b ^ 0xFF for b in P])         # побитовая инверсия вызова партнёра
Block_ans = C4 + bytes([cfg]) + not_P + c7a      # 4 + 1 + 4 + 7 = 16 байт (0x00138E26)
ans_frame = MAC(K_n, Block_ans, ID_ac) + b"\x00\x00\x00" + bytes([S])
```
`ECU` и `TCU` на своей стороне считают ожидаемый `MAC(K_n, Block_ans, ID_ac)`, сверяют `ans_frame[0:4]` и проверяют младший бит статуса `S & 0x01 == 1` (в штатном режиме при опознанном ключе и загруженных слотах `S = 0x1F`) — это и есть криптографическая санкция на пуск двигателя и замыкание сцеплений.

> **Эталонный вектор для самопроверки кода (ac-immo-she.md` §4.10.2):**
> При `A = b"LAB IMMO SLOT A!"`, `B = b"LAB IMMO SLOT B!"` (`K0 = b"LAB IMMO SLOT A!"`), `cfg = 0x4C`, `ID_p = b"L0"`, `ID_ac = b"LA"` и вызове `P = 01 02 03 04`:
> * запрос `0x010` = `01 02 03 04 9d fa 63 74`
> * ответ `0x011` = `e7 7f 80 a4 00 00 00 1f`

### 3. Формулы пакетов привязки по диагностике (`2E 02F7` и `2E 02E1`)

Обратите внимание на разницу порядка байтов контрольных сумм: в кадрах иммо на CAN (`0x010..0x01F`) и в `EEL 0x68` `CRC-32` идёт **младшим байтом вперёд (Little-Endian)**, а в диагностических UDS-запросах `2E 02F7` и `2E 02E1` — **старшим байтом вперёд (Big-Endian)**.

#### 3.1. Заливка данных иммобилайзера `2E 02 F7` (87 байт, data_02f7)
Собирается открытый 80-байтовый буфер `P[0..79]` (ac-immo-diag.md` §4.3, ac-immo-data.md` §2.4):
* `P[0x00 : 0x11]` (17 Б) — `VIN`
* `P[0x11 : 0x21]` (16 Б) — `S0` (см. п. 1.1)
* `P[0x21 : 0x31]` (16 Б) — `S1`
* `P[0x31 : 0x41]` (16 Б) — новый `K_c` (обычно оставляют равным текущему `K_c`)
* `P[0x41]` (1 Б) — байт `cfg` (`Power Class` в `MAC`)
* `P[0x42]` (1 Б) — `(n_keys & 0x0F) | (p7 << 6) | (p6 << 7)` (число разрешённых ключей `1..8` и флаги наличия партнёров 6, 7)
* `P[0x43]` (1 Б) — битовая раскладка `0x0013A99C`:
* бит 0 (`0x01`): `0` = своя катушка приборки, `1` = ключ по CAN (`KESSY`)
* бит 1 (`0x02`): выключить окно повторного пуска
* биты `2..7` — какие партнёры задействованы в машине (`0xFEDF52F7`): бит 2 (`0x04`) → п5, бит 3 (`0x08`) → **п1 (`TCU`)**, бит 4 (`0x10`) → **п0 (`ECU`)**, бит 5 (`0x20`) → п2, бит 6 (`0x40`) → п3, бит 7 (`0x80`) → п4. Например, для связки `ECU (п0) + TCU (п1)` со своей катушкой `P[0x43] = 0x18`.
* `P[0x44 : 0x50]` (12 Б) — `0x00` (`P[0x44]` — транзитный байт, `0x45..0x4F` не используются).

Шифрование **текущим** `K_c` приборки (5 блоков по 16 Б в ECB) и сборка UDS-сообщения:
```python
X   = b"".join(AES128(Kc_cur, P[i : i + 16]) for i in range(0, 80, 16))  # 80 байт
K   = CRC32(P).to_bytes(4, "big")                                        # 4 байта BE!
uds = b"\x2E\x02\xF7" + X + K                                            # 87 байт
```

#### 3.2. Команда `2E 02 E1 <M0 M1> <C> <Param>` и запуск обучения `ID` партнёров (`C = 0x04`)
1. Тестер читает открытый 4-байтовый одноразовый вызов `R[0..3]` запросом `22 02 E0` → ответ `62 02 E0 R0 R1 R2 R3`.
2. Вычисляется 2-байтный `MAC` на `K_c` (mac_02e1):
   ```python
   blk16 = bytes([C, Param]) + R + c10       # 1 + 1 + 4 + 10 = 16 байт (0x0013AF30)
   crc16 = CRC16(AES128(Kc, blk16))          # CRC-16/CCITT-FALSE по шифротексту
   M0, M1 = (crc16 >> 8) & 0xFF, crc16 & 0xFF
   uds_cmd = bytes([0x2E, 0x02, 0xE1, M0, M1, C, Param])
   ```
   *(Проверочный вектор из прогона ac-immo-diag.md` §12: при `Kc = b"LAB IMMO KC KEY!"`, `C = 0x10`, `Param = 0x01`, `R = 2a e9 15 69` получается `M0 M1 = 14 db`.)*
3. Для команды запуска обучения `ID` партнёров **`C = 0x04`** биты `Param` (`0..7`) переводятся таблицей `0x0019D160` (`0x0013A664`, ac-immo-data.md` §2.2) в маску обучения `0xFEDF52B2`:
   * бит 0 (`0x01`) → п6, бит 1 (`0x02`) → п5, **бит 2 (`0x04`) → п1 (`TCU`)**, бит 3 (`0x08`) → п4, бит 4 (`0x10`) → п3, **бит 5 (`0x20`) → п2 (`TCU`)**, **бит 6 (`0x40`) → п0 (`ECU`)**, бит 7 (`0x80`) → п7.
   * То есть для одновременного обучения `ECU` (п0) и `TCU` (п1) подаётся `C = 0x04, Param = 0x44` — после чего достаточно двух очередных кадров `0x010` и `0x012` с новым `P` от эмулируемых `ECU` и `TCU`, чтобы приборка вычислила и записала их `ID` по формуле п. 2.3.

# Спецификация протокола иммобилайзера (WFS5) приборки `fpke` (`5E0920790A`, SW `1703`) для эмулятора ECU / TCU / тестера

Документ содержит все константы ПЗУ приборки, лабораторные ключи стенда (`IMMO_LAB`), формулы вычисления ключей/MAC/пакетов привязки и эталонные тест-векторы. Бинарники приборки не требуются.

---

## 1. Шина CAN и адресация

Шина — приводной/комфортный CAN приборки (`500 кбит/с`, классический CAN 2.0, `DLC = 8`, без E2E):

| Назначение | CAN ID (кто → кому) | Формат |
|---|---|---|
| **Партнёр 0 (группа Б — `ECU` двигателя)** | `0x010` (ECU → приборка), `0x011` (приборка → ECU) | 11-bit, 8 Б |
| **Партнёр 1 (группа Б — обычно `TCU` / КП)** | `0x012` (TCU → приборка), `0x013` (приборка → TCU) | 11-bit, 8 Б |
| **Партнёр 2 (группа Б — альт. `TCU` / силовой узел)** | `0x014` → `0x015` | 11-bit, 8 Б |
| **Партнёры 3, 4 (группа Б)** | `0x016` → `0x017`, `0x018` → `0x019` | 11-bit, 8 Б |
| **Партнёры 5, 6, 7 (группа А — напр. `ELV`)** | `0x01A` ↔ `0x01B`, `0x01C` ↔ `0x01D`, `0x01E` ↔ `0x01F` | 11-bit, 8 Б |
| **Ключ по CAN (`KESSY` ↔ приборка)** | `0x155`, `0x157` (приборка → узел), `0x29D` (узел → приборка) | 11-bit, 8 Б |
| **Канал 3 ISO-TP (передача слотов `80 03` / клиент `0x0E`)** | `0x17FA0E14` (узел → приборка), `0x17F8140E` (приборка → узел) | 29-bit ISO-TP |
| **Канал 2 ISO-TP (защита компонентов `J533`)** | `0x17FC0114` (шлюз → приборка), `0x17FE0114` (приборка → шлюз) | 29-bit ISO-TP |
| **Канал 4 ISO-TP (диагностика UDS приборки)** | `0x714` (тестер → приборка), `0x77E` (приборка → тестер), pad `0xAA` | 11-bit ISO-TP |

## 4. Криптографические примитивы

1. **`AES128(key16, block16)`** — стандартное шифрование одного 16-байтового блока **AES-128** (FIPS-197, ECB без IV и padding).
2. **`CRC32(data)`** — стандартный отражённый **IEEE 802.3 CRC-32** (`zlib.crc32(data) & 0xFFFFFFFF`, полином `0xEDB88320`, `init = 0xFFFFFFFF`, `xorout = 0xFFFFFFFF`; тест: `CRC32(b"123456789") == 0xCBF43926`).
3. **`CRC16_CCITT(data)`** — **CRC-16/CCITT-FALSE** (полином `0x1021`, `init = 0xFFFF`, без отражения, `xorout = 0x0000`; тест: `CRC16_CCITT(b"123456789") == 0x29B1`).

> **Важно про порядок байтов CRC:**
> * В кадрах иммобилайзера на CAN (`0x010..0x01F`) и в `EEL 0x68` `CRC-32` раскладывается **младшим байтом вперёд (Little-Endian, `<I`)**.
> * В диагностических запросах UDS (`2E 02F7` и `2E 02E1`) `CRC-32` и `CRC-16` передаются **старшим байтом вперёд (Big-Endian, `>I` / `>H`)**.

## 5. Производные ключи партнёров `K_n` и перестановка `S0, S1 ↔ A, B`

### 5.1. Упаковка `S0, S1` (для `2E 02F7`) ↔ `A, B`
Операция является инволюцией (прямое и обратное преобразования совпадают):
```python
S0 = A[0:4] + B[4:12] + A[12:16]
S1 = B[0:4] + A[4:12] + B[12:16]

A  = S0[0:4] + S1[4:12] + S0[12:16]
B  = S1[0:4] + S0[4:12] + S1[12:16]
```

### 5.2. Формулы 16-байтовых ключей партнёров `K_n` из слотов `A` и `B`

*(Внимание: в строках `IMMO_LAB` слоты `A` и `B` отличаются только 14-м байтом `'A'`/`'B'`, поэтому для `IMMO_LAB` часть ключей численно совпадает со слотом `A` или `B`. Для произвольных случайных `A` и `B` при новой адаптации все `K_n` будут разными — реализуйте именно нарезку по индексам!)*

| Партнёр | Кадры CAN | `n` | Склейка байтов из `A[0..15]` и `B[0..15]` | Значение для `IMMO_LAB` (hex) |
|---|---|---|---|---|
| **Партнёр 0 (`ECU`)** | `0x010` → `0x011` | `0` | `A[0:4] + B[4:12] + A[12:16]` | `4c 41 42 20 49 4d 4d 4f 20 53 4c 4f 54 20 41 21` |
| **Партнёр 1 (`TCU`)** | `0x012` → `0x013` | `1` | `B[0:4] + A[4:7] + B[7:12] + A[12:16]` | `4c 41 42 20 49 4d 4d 4f 20 53 4c 4f 54 20 41 21` |
| **Партнёр 2 (`TCU`)** | `0x014` → `0x015` | `2` | `B[0:2] + A[2:4] + B[4:12] + A[12:14] + B[14:16]` | `4c 41 42 20 49 4d 4d 4f 20 53 4c 4f 54 20 42 21` |
| **Партнёр 3** | `0x016` → `0x017` | `3` | `A[0:6] + B[6:10] + A[10:16]` | `4c 41 42 20 49 4d 4d 4f 20 53 4c 4f 54 20 41 21` |
| **Партнёр 4** | `0x018` → `0x019` | `4` | `B[0:1] + A[1:4] + B[4:7] + A[7:9] + B[9:12] + A[12:15] + B[15:16]` | `4c 41 42 20 49 4d 4d 4f 20 53 4c 4f 54 20 41 21` |
| **Партнёр 5 (гр. А)** | `0x01A` ↔ `0x01B` | `5` | `A[0:16]` | `4c 41 42 20 49 4d 4d 4f 20 53 4c 4f 54 20 41 21` |

## 6. Рукопожатие группы Б (`ECU` / `TCU`) и вычисление `ID` при привязке

### 6.1. Функция `MAC(K_n, Block16, sender_id2)` → 4 байта
```python
def mac(key16: bytes, block16: bytes, sender_id2: bytes) -> bytes:
   ct = aes128_encrypt(key16, block16)
   crc = zlib.crc32(ct) & 0xFFFFFFFF
   c0 = crc & 0xFF
   c1 = (crc >> 8) & 0xFF
   c2 = (crc >> 16) & 0xFF
   c3 = (crc >> 24) & 0xFF
   return bytes([c0, c1, c2 ^ sender_id2[0], c3 ^ sender_id2[1]])
```

### 6.2. Кадр запроса `ECU` / `TCU` → приборка (`0x010`, `0x012`, `0x014`, каждые ~100 мс)
Ведомый блок выбирает 4 байта вызова `P[0..3]` (счётчик или ГПСЧ):
```python
C4  = bytes.fromhex("9cf7feb7")
c7p = bytes.fromhex("01020304050607")

block_req = C4 + bytes([cfg]) + P + c7p        # ровно 16 байт
tx_can    = P + mac(K_n, block_req, ID_p)      # 8 байт на шину
```

### 6.3. Как приборка проверяет запрос и обучает `ID_p` партнёра
Получив `rx[0..7]`, приборка берёт `P = rx[0:4]`, считает `c0, c1, c2, c3 = CRC32_LE(AES128(K_n, block_req))`:
1. **Проверка знания ключа `K_n` и байта `cfg`:** `rx[4] == c0` и `rx[5] == c1`.
2. **Восстановление 2-байтного `ID` отправителя из кадра:**
   ```python
   ID_cand = bytes([rx[6] ^ c2, rx[7] ^ c3])
   ```
3. **Режим работы vs обучение:**
   * В штатном режиме приборка проверяет `ID_cand == ID_stored`.
   * Если для этого партнёра включён бит обучения (после UDS-команды `2E 02E1 <MAC> 04 <Param>`), приборка на 1-м кадре с верными `c0, c1` запоминает `(P_1, ID_cand_1)`. Если в следующем кадре с **новым вызовом** `P_2 != P_1` снова сошлись `c0', c1'` и получилось **`ID_cand_2 == ID_cand_1`**, приборка записывает `ID_cand` в свой NvM (`EEL 0x66`) как обученный `ID` этого партнёра и сбрасывает бит обучения.

### 6.4. Кадр ответа приборки → `ECU` / `TCU` (`0x011`, `0x013`, `0x015`, через ~20 мс)
```python
c7a   = bytes.fromhex("08090a0b0c0d0e")
not_P = bytes([b ^ 0xFF for b in P])           # побитовая инверсия P

block_ans    = C4 + bytes([cfg]) + not_P + c7a # ровно 16 байт
expected_mac = mac(K_n, block_ans, ID_ac)      # 4 байта
# Кадр приборки (8 байт): expected_mac + b"\x00\x00\x00" + bytes([S])
```
**Условие разрешения пуска в эмуляторе `ECU` / `TCU`:**
* `rx_ans[0:4] == expected_mac`
* `(rx_ans[7] & 0x01) == 1` (в полной норме `S = 0x1F`; `0x08` — ключ зажигания не опознан или слоты `A/B` не загружены; `0x18` — не совпали `MAC` или `ID` партнёра).

## 7. Формулы диагностических пакетов привязки (`0x714` → `0x77E`)

### 7.1. Запись конфигурации и секретов `2E 02 F7` (87 байт)
Формируется 80-байтовый открытый буфер `P_buf[0..79]` (неиспользуемые байты = `0x00`):
* `P_buf[0x00 : 0x11]` (17 Б) — `VIN` (например `b"LABVIN01234567890"`)
* `P_buf[0x11 : 0x21]` (16 Б) — `S0 = A[0:4] + B[4:12] + A[12:16]`
* `P_buf[0x21 : 0x31]` (16 Б) — `S1 = B[0:4] + A[4:12] + B[12:16]`
* `P_buf[0x31 : 0x41]` (16 Б) — новый `Kc` (оставляем `Kc_cur`)
* `P_buf[0x41]` (1 Б) — `cfg` (`0x4C` для `IMMO_LAB`)
* `P_buf[0x42]` (1 Б) — `(n_keys & 0x0F) | (p7 << 6) | (p6 << 7)` (число разрешённых ключей `1..8`, старшие биты — наличие партнёров 6 и 7)
* `P_buf[0x43]` (1 Б) — флаги и маска задействованных партнёров:
* бит 0 (`0x01`): `0` = своя катушка приборки, `1` = ключ по CAN (`KESSY` / лабораторный узел ключа `immo-lab=on`)
* бит 1 (`0x02`): выключить окно повторного пуска
* бит 2 (`0x04`): партнёр 5
* бит 3 (`0x08`): **партнёр 1 (`TCU`)**
* бит 4 (`0x10`): **партнёр 0 (`ECU`)**
* бит 5 (`0x20`): **партнёр 2 (альт. `TCU`)**
* бит 6 (`0x40`): партнёр 3
* бит 7 (`0x80`): партнёр 4
*(Пример: `ECU (п0) + TCU (п1)` и ключ по CAN → `0x01 | 0x10 | 0x08 = 0x19`; со своей катушкой → `0x18`.)*
* `P_buf[0x44 : 0x50]` (12 Б) — `0x00`.

Пакет UDS (шифруется **текущим** `Kc` приборки поблочно в ECB, `CRC-32` открытого текста — **Big-Endian**):
```python
X   = b"".join(aes128_encrypt(Kc_cur, bytes(P_buf[i : i + 16])) for i in range(0, 80, 16))
K   = (zlib.crc32(P_buf) & 0xFFFFFFFF).to_bytes(4, "big")
uds = b"\x2E\x02\xF7" + X + K   # 87 байт (ISO-TP: FF + 12 CF)
```
*(Внимание: запись `2E 02F7` переводит приборку в режим 2 и стирает список ключей — после неё нужно либо обучить ключ `2E 02E1 00 00 40 00` → `2E 02E1 00 00 80 00`, либо для обучения одних только `ID` партнёров на уже обученной в режиме 1 приборке **не слать `02F7`**, а сразу подать команду `2E 02E1` с `C = 0x04` ниже, если биты нужных партнёров уже включены в `0xFEDF52F7`.)*

### 7.2. Команда управления `2E 02 E1 <M0 M1> <C> <Param>` (7 байт)
1. Запросить текущий 4-байтовый вызов `R`: отправить `22 02 E0` → получить `62 02 E0 R0 R1 R2 R3`.
2. Посчитать 2-байтный `MAC` (**Big-Endian** `CRC-16/CCITT-FALSE`):
   ```python
   c10   = bytes.fromhex("01020304050607080910")
   blk16 = bytes([C, Param]) + R + c10               # 1 + 1 + 4 + 10 = 16 байт
   crc16 = crc16_ccitt(aes128_encrypt(Kc, blk16))
   uds   = bytes([0x2E, 0x02, 0xE1, crc16 >> 8, crc16 & 0xFF, C, Param])
   ```
3. Для команды **`C = 0x04` (включить обучение `ID` партнёров)** биты байта `Param` отображаются по таблице `T_04 = [6, 5, 1, 4, 3, 2, 0, 7]`:
   * `0x01` (бит 0) → п6
   * `0x02` (бит 1) → п5
   * `0x04` (бит 2) → **п1 (`TCU`)**
   * `0x08` (бит 3) → п4
   * `0x10` (бит 4) → п3
   * `0x20` (бит 5) → **п2 (альт. `TCU`)**
   * `0x40` (бит 6) → **п0 (`ECU`)**
   * `0x80` (бит 7) → п7
   *(Пример: обучить `ECU` п0 — `Param = 0x40`; обучить `ECU` п0 + `TCU` п1 одновременно — `Param = 0x44`.)*

## 8. Дополнительно: узел ключа по CAN (`0x155`/`0x157` → `0x29D` + канал 3 `80 03`)

Если на стенде нет отдельного узла ключа (`immo-lab=on` выключен) и нужно подать в приборку валидный ключ по CAN (при бите 7 `0xFEDF5303 = 1`):
1. Приборка шлёт `0x155`: `ff ff ff ff ff 02 ff ff`.
2. Узел отвечает `0x29D`: `ID_key[3] ID_key[2] ID_key[1] ID_key[0] ff ff 00 04` (для `"LK01"` → `31 30 4b 4c ff ff 00 04`).
3. Приборка шлёт пару кадров: `0x157` = `R[0..7]` (8 байт вызова) и `0x155` = `ff h1[0..3] 05 ff ff`, где:
   ```python
   c8 = bytes.fromhex("6abb48239fb3ca85")
   C  = aes128_encrypt(Kc, R + c8)
   h1 = bytes(C[8 + i] ^ C[i]     for i in range(4))   # доказательство приборки
   h2 = bytes(C[12 + i] ^ C[4 + i] for i in range(4))  # ответ узла ключа
   ```
4. Узел отвечает `0x29D`: `h2[0..3] ff ff 10 08` (слот ключа 1).
5. Узел отправляет по ISO-TP на `0x17FA0E14` (ответы FC/SF от приборки на `0x17F8140E`) 34-байтовое сообщение со слотами:
   ```python
   msg34 = b"\x80\x03" + aes128_encrypt(Kc, A) + aes128_encrypt(Kc, B)
   ```
