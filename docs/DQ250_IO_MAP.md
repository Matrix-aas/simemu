# DQ250 0D9 (TC1766): карта входов/выходов, устройства платы, состояние «ТКУ в контуре»

Дата: 2026-11-02 (третий проход по DQ250). Прошивки не изменялись; RAM прошивок только читалась (наблюдение). Адреса —
образ `0D9300011R_4319.bin` (далее 4319), если не сказано иначе; тюнинговый `0D9300012F_4930.bin`
(0D9300012F/4930) — тот же SBOOT/CBOOT и то же железо, но другие адреса ASW/CAL. Метки — как в
`docs/SIMOS18_GPTA_IO_RE.md` §0: `VERIFIED-S` (статически), `VERIFIED-T` (эмулятор), `HYP`; в коде — `UNVERIFIED`.
Код: `crates/simemu-tc1791/src/dq250_io.rs` (устройства и характеристики), `tcu_dq250.rs` (плата), studio —
`crates/simemu-cli/src/studio/tcu_io.rs` (`TcuBoard`, `dq250_inputs`, сценарий `dq250_drive_scenario`).

## 0. Кратко

- Плата DQ250 работает в studio вместо DQ200, когда КПП сборки — DQ250 0D9 (`octavia_is38`, `golf7r`):
  `TcuBoard::{Dq200, Dq250}`, `StudioSession::boot_dq250` (дозапись CRC §2.4 п.3 AGENTS.md, лабораторная привязка
  `immo_lab::bind_dq250_tcu`), CAN автомобиля на узле 1 MultiCAN.
- Эмулированы датчики (обороты 5 каналов, ход 4 актуаторов, давления K1/K2, температуры), сторожевая микросхема на SSC1,
  SPI-термодатчик на SSC0/P2.9, питание силовых каскадов, 3 high-side ключа, 11 катушек клапанов с датчиками тока.
- Результат (`dq250_drive_scenario`, оба образа, `VERIFIED-T`): WFS5 принят; в P прошивка включает R и 2-ю
  (предвыбор), в D выводит R, включает 1-ю (`WBA_03` = 1) и трогается на K1 (ползёт ~6–8 км/ч). Под педалью при ~13 км/ч
  прошивка сбрасывает K1 и целевую передачу, K2 не включает — **переключений вверх нет** (§7).
- Модель GPTA декодировала массив мультиплексора TC1766 со сдвигом (54 слова вместо 52) — исправлено (§2).
- Четвёртый проход (2026-11-02, образ 0D9300012F 0D9300012F/4930): сервис по UDS как в мастерской — кодирование 000024
  и базовые установки 0x0380 / 0x04D4 выполняет сама прошивка, результат она же хранит в EEPROM; EEPROM платы
  сохраняется между включениями и запусками studio (§8). Датчики оборотов — по углу зубчатого колеса (§6), упор 5/N на
  стороне N (§4), вход AIN25 (§6). Переключений вверх по-прежнему нет (§7).

## 1. Метод

- Ghidra 12.1.4 headless (TriCore `tc176x`), rizin (линейный листинг), пробы и трассы эмулятора (`dq250_explore`,
  `SIMEMU_TCU_WATCH/_PROBES` сценария), RAM-диффы при изменении одного входа. REA (`reverse-engineer-anything`) —
  как маршрутизатор; ELF TriCore REA не открывает (как на DQ200).
- Таблицы DTC: `tcu_dq250::dtc_table` (номер VAG → SAE). События ПО: событие `0x1nn` ↔ запись `nn` таблицы CAL
  `0x800387E0` (`VERIFIED-S` для 0x100..0x10C, 0x11A/B, 0x134/135, 0x142, 0x157, 0x16B, 0x16E, 0x170, 0x17E).

## 2. GPTA0: маршрутизация входов (`VERIFIED-T`)

Прошивка пишет ровно 52 слова MRADIN между сбросом массива (MRACTL = 2) и включением (0x3401): 28 OMCR + 16 LIMCR +
8 GIMCR. Модель ожидала 54 (TC1791/TC1784) — все маршруты были сдвинуты на группу. `Gpta::tc1766` (52 слова),
`engine_io::omcr_sources` — 28 OMCR-слов, группы 13..0. После исправления:

| Ячейка | Вход | Ячейка | Вход |
| :-- | :-- | :-- | :-- |
| GTC00 | FPC0 ← IN0 | LTC00 | IN1 |
| GTC02 | FPC1 ← IN2 | LTC01 | IN3 |
| GTC04 | FPC5 ← IN10 | LTC02 | IN7 |
| GTC06 | FPC3 ← IN6 | LTC08 | IN9 |
| GTC08 | FPC4 ← IN8 (фильтр 768 тиков) | LTC09 | IN11 |
| GTC10 | FPC5 | GTC18/19, GTC24 | IN22, IN24 (без захвата — не датчики) |

Таймеры всех ШИМ-групп совпадают с таблицей частот драйвера Pwm (0x800DC97C): fGPTA = 40.025 МГц (`VERIFIED-S`).

- `VERIFIED-S`: ячейка → OUT (OMCR), PCS-буква ↔ L0..L3 (диагностика 0x80047AD0), выходы 0..3 ↔ буквы (0x800DBAF4),
  N92 ↔ P2.0 (проверка остаточного тока HS3 0x80046434), группировка по HS. `HYP`: буквы → номера N (порядок SSP 308),
  OUTk ↔ P1.(k−16) / OUT73/75 ↔ P1.1/P1.3 (даташита TC1766 нет; согласуется с IOCR).
- Датчики тока: PCS 0.4884 мА/код = 1.65 В/А (`I[0.1 мА] = code·40010 >> 13`), суммы HS1/HS2 AIN29/AIN5 0.5 В/А, HS3 AIN3
  1.0 В/А (`VERIFIED-S`; единицы `HYP`).
- Модель платы (`dq250_io::VALVES`, `tcu_dq250::dq250_valves`): катушка R-L на каждый клапан, интегрирование точно по
  фронтам ячеек GPTA (`engine_io_sync` → `dq250_valve_edge`) и по записям портов; ток катушки — на свои датчики.
  «Выход высокий = ключ открыт» (`HYP`, подтверждено замкнутыми токовыми контурами прошивки, `VERIFIED-T`). R катушек —
  из plant (`tcu_io::coil_params`), L — `SolenoidHw` plant (`UNVERIFIED`).
- Характеристики клапанов прошивки (`FUN_800c7014`, коэффициенты по умолчанию 0x800DD248, `VERIFIED-S`): K1/K2
  `I[А] = 0.1·p[бар]` выше 0.1 бар; N217 `I = 1 − 0.05·p` (20 бар обесточен). Plant DQ250 использует их
  (`WetHydraulicsHw::clutch_valve_pa_per_a`, `main_valve_linear`) — с прежним законом (16 бар, зона 8 %) давление K1
  было на ~25 % выше команды.
- 0D9300012F (шестой проход, `VERIFIED-S`): та же таблица по 0x800C44EC, копия в RAM 0xD0003418 (`0x800A7144`, если блоки
  NVM 0xD00034A4/0xD00034E0 недействительны), расчёт тока `0x800AE4C4`: давление 0xD0003468[клапан] (мбар) → ток
  0xD0003478 (0.1 мА). Давление K1/K2 задаёт модель сцепления прошивки (момент → давление, `FUN_8009e4ac`) —
  `docs/DQ250_FIRMWARE_SPEC.md` §3; 0xD000348C/0xD000349C в 4930 — не команды давления.

## 4. Актуаторы передач (`VERIFIED-S`, кроме мультиплексора)

- Актуаторы 0..3 = 1/3, 4/2, 5/N, 6/R. Класс положения (0x8009CBB8, таблица 0x800DBA8C): ход ≤ −6.50 мм → класс 1
  (передачи 0x800DBA0A = 3, 2, N, R), ≥ +6.50 мм → класс 2 (0x800DBA0E = 1, 4, 5, 6); подкоробки 0x800DBA12/16 =
  [0, 1, 0, 0] / [0, 1, 0, 1] (R — на K1). Plant: `forks = [(0,1,3), (1,4,2), (0,5,N), (1,6,R)]`,
  `fork_minus_shaft[3] = 0`, N-сторона 5/N — фиксатор на том же ходе, что передачи (`free_side_mm`, ход `HYP`).
- Камеры: регулятор хода (0x800A4680 → `FUN_800abc54` → `FUN_8009e184`) подаёт команду в камеру +0x2C для цели класса 1
  (−) и +0x2E для класса 2 (+); выходы камер 0x800DBA02 = [1, 2, 1, 3] (+0x2C), 0x800DBA06 = [0, 3, 0, 2] (+0x2E).
- Сторона N актуатора 5/N: хода за нейтраль нет (`free_side_mm` = 0.5 мм для DQ250, значение `UNVERIFIED`). Основание
  (0D9300012F, `VERIFIED-S/T`): адаптация точек синхронизации 0x04D4 (0x8005B814, шаг 8) для актуатора 2 / стороны 1
  принимает замер, когда вилка НЕ сдвинулась (± 250 ед. ≈ 0.9 мм), и требует нейтраль, усреднённую по обеим сторонам, в
  окне CAL 0x800383F0 (шаг 9); с прежним упором 8.8 мм (HYP предыдущего прохода) процедура обрывалась с кодом 9.
- Мультиплексор N92 (`HYP`, `WetHydraulicsHw::mux_energised`): обесточен — клапаны на 1/3 и 6/R, под током — на 4/2 и 5/N.
  Единственная из проверенных группировок, при которой прошивка завершает свои запросы (`VERIFIED-T`): в P — N89 + N92 для
  2-й, N91 без N92 для R; в D — N88 без N92 для 1-й. Варианты {1/3,4/2}/{5/N,6/R} включали 6-ю или 5-ю вместо R/1-й.
- Датчики хода AIN16..19 (VAREF[2] = 5 В питания датчиков, `HYP`): характеристика CAL 0x80030400 (мВ) / 0x80030424
  (0.01 мм), 17 точек; модель — обратная к ней (`dq250_io::travel_sensor_v`); окно 300..4700 мВ (иначе P0607
  0x29A2..A8).

## 5. Устройства SPI

- **Сторож на SSC1, CS P2.1** (канал 0x800DCA24: 16 бит, CON 0xC01F) — `dq250_io::QaWatchdog`. Ответ в том же кадре
  (`VERIFIED-S`): `E800` → биты 6:4 счётчик ошибок, 3:0 вопрос; `EA00` → 0xC0; четыре ответа `0xF0xx` (коды 3,2,1,0,
  `FUN_8009f1cc`, векторы q=0: F0FF F00F F0F0 F000 — тест `watchdog_answers_match_the_firmware_vectors`); `D401`
  реинициализация, `D417`, `D010`, `D276`/`D246` (рег. 0x12, `HYP`: биты 5:4 = разрешение силовых каскадов), `D0D0`
  перед выключением; `C800`/`EC00`/`F600` — статус, 0 = норма. После 200 циклов прошивка нарочно отвечает неверно и
  ждёт счётчик +1 — модель это делает. `UNVERIFIED`: счётчик при включении 0, порядок вопросов, разрешение по рег. 0x12.
- **Питание силовых каскадов**: P3.10 = 1, P3.9 = 0 и разрешение сторожа → AIN4/AIN6 = KL30/6 (самотест 0x8009D61C,
  CAL 0x80034262/64; `VERIFIED-S/T`: ранее флаг 0xD00038DC = 4 → P0607 0x2AB3, теперь нет).
- **SPI-термодатчик на SSC0, CS P2.9** (LM74-подобный, `HYP` сильная): ID 0x800F, `T = ((rx + 0x2CC0) >> 7) − 0x59` °C,
  младшие два бита должны быть ненулевыми (`FUN_8008add8`) → тепловая модель ASW. Модель: температура ATF
  (мехатроник в масле, `HYP`).

Датчики оборотов (2026-11-02): линия GPTA следует углу зубчатого колеса (`tcu_dq250::PinGen`): фронт ровно при
прохождении края зуба, стоящее колесо держит уровень, колебание внутри шага не даёт фронтов, реверс пересекает тот же
край обратно (фаза B выхода — ¼ шага позади A при вращении вперёд, `HYP`). Прежняя модель (меандр с частотой |об/мин|)
превращала дребезг вала в люфтах при P (± 10 об/мин на выходе, физика) в непрерывную «скорость»: ТКУ видела движение
(0xD000326A ≈ 100, бит 2 условий 0xD00059B0), и базовая установка 0x0380 получала NRC 0x22 (`VERIFIED-T`). Гистерезис
датчика Холла не моделируется.

AIN25 (0D9300012F): 10-й элемент таблицы напряжений платы (каналы 0xD0005FA0: 0x19, усиление 1.0 → 0xD0003B2A, мВ);
события 0x167 / 0x165 (в таблице событий — P0602, номера VAG 0xEBC7/0xEBxx, в `19 02` не попадают) — ниже 1000 / 3100 мВ
(0x800A4C04, CAL 0x80030042/40, `VERIFIED-S`). Вход не подавался (0 В) — отсюда «постоянные P0602» прошлых проходов;
кодирование на них не влияет. Подаётся 3.2 В (`UNVERIFIED`, HYP: контроль шины 3.3 В): ветка «пройдено» 0x800A4C32
исполняется, 0x800A4C28 — нет (`VERIFIED-T`, `dq250_explore`).

Передаточные числа — таблица зубьев CAL, найдена по структуре (`tcu_dq250::gear_set`, тест
`dq250_calibration_constants`): 4319 — 38/13, 44/24, 34/26, 31/32, 28/27, 26/32, главные 62/13 (1–4) и 62/18 (5, 6, R),
R = 27·22/(14·13); 4930 (стенда) — 45/13, 41/20, 39/30, 37/41, 32/35, 31/41 (набор 02E), главные 70/16 и 70/21,
R = 33·22/(14·13). Профиль `dq250_0d9_awd` = набор 4930, радиус шины 0.310 м (эталонный лог при 70/16).

## 7. Состояние «в контуре» и DTC

`dq250_drive_scenario` (`octavia_is38`, SC8O40, road-load-стенд; native, 30 с; оба образа одинаково):
- WFS5: 1 вызов, принят. P: актуатор 4/2 → −8.8 мм (2-я), 6/R → −8.8 мм (R); RAM `0xD00048C8` = [07 07 07 ..
  02 02 02] (подкоробка 1: R, подкоробка 2: 2-я — цель = факт).
- D (10 с): R выведена, 1-я включена, `WBA_03` = 1, `0xD00048C8` = [01 01 01 .. 02 02 02]; после отпускания тормоза —
  K1 ~3–4 бар, ползёт до 6–8 км/ч.
- Педаль 30 % (16 с): K1 до ~4–5 бар, 1500 об/мин, 13 км/ч; затем (~1.4 с) прошивка плавно снимает команду K1
  (`0xD000348C` → 0), выход N233 62 % → 16 %, `GE_Zielgang` 1 → 0; K2 не заполняется (N371 в дежурных 15 %), двигатель
  уходит в отсечку; через ~10 с цикл повторяется. Запросов вмешательства по моменту нет (`GE_MMom_Status` 0), флаги
  отключения подкоробок `0xD000591E/F` = 0, новых событий нет (постоянно сообщаются только 0x121/0x167 = P0602 —
  кодирование/адаптации пустого EEPROM). Причина не установлена; кандидаты (`HYP`): отсутствие адаптаций
  (точки касания сцеплений, «базовые установки») и кодирования в стёртом EEPROM; правдоподобие датчиков входа (P0717,
  статус 0x42).

После кодирования и базовых установок (§8; `dq250_drive_scenario` с `SIMEMU_DQ250_NVM_DIR` = EEPROM после мастерской,
2026-11-02, native) картина та же: при ~13 км/ч под педалью 30 % режим КПП 0xD0005E13 переходит 7 → 1 (в P/N тоже 1,
стоя в D — 5/6, в движении — 7), `WBA_03` = 10, `GE_Zielgang` 0, K1 сбрасывается, N215/N216 не управляются, N233/N371
падают до ~0.3 А, двигатель уходит в отсечку. Единственное событие отказа в этом окне — 0x121 (проба на 0x800804CC, каждые
2 мс). Найдено (`VERIFIED-S`): 0x121 — значения адаптации точек касания 0xD0003C34 (по два на сцепление, смещения к CAL
0x80032BD8+0x15C = 750 / 1050) ≤ CAL+0x16E (0); их учит автоматическая адаптация (состояние 0xD0003C85, 0x800669AC,
вызов из 0x80080A28), а не базовая установка; на стенде она ни разу не стартовала: биты условий 0xD0003C62 — обороты
двигателя вне 800..1800 (CAL+0x14A/+0x14C; холостой ~700–780), режим 0xD0005E13 ≠ 9, 0xD0005E14 < 2, бит 9 (`VERIFIED-T`).
Сброс 0x0317 записывает в них CAL+0x17A/+0x17C = 0 — событие остаётся. Стоя в D с тормозом прошивка перебирает 1 ↔ 2
(`GE_Zielgang` 2, K2 ~2.5 бар; так было и на базовом коммите — `drive21.log` прошлого прохода), обороты холостого
проседают до 260–560, после мастерской двигатель может заглохнуть. Причина перехода 7 → 1 не найдена (писатели
0xD0005E13 — через базу 0xD0005E10, не разобраны). Кандидаты (`HYP`): не выполненная адаптация точек касания;
несоответствие физики сцепления модели прошивки (у plant K1 точка касания 1.1 бар и ~98 Н·м/бар — при 4 бар сцепление
замкнуто без проскальзывания при 70 Н·м двигателя; характеристику момент→давление прошивки не нашёл).

Пятый и шестой проходы (`docs/DQ250_FIRMWARE_SPEC.md`): переход 7 → 1 — направление выхода (порт P0), исправлено; «не
выше 2-й» на стёртом EEPROM — штатное ограничение прошивки без базовых установок (§5.4 спецификации); просадка/заглохание
стоя в D и в конце торможения — пакет сцеплений plant замыкался на 1.5 бар раньше и был вдвое «сильнее» характеристики,
на которую откалибрована прошивка (§3 спецификации), подогнан. Полный заезд — `dq250_full_drive_scenario`.

DTC в конце сценария (`19 02`, по таблице образа):

## 8. UDS приложения: кодирование, базовые установки, EEPROM (0D9300012F, 2026-11-02)

Адреса — образ 0D9300012F 0D9300012F/4930. Реверс: Ghidra 12.1.4 headless (`tc176x`), линейный листинг rizin; проверка —
запросы тестера по CAN 0x7E1 → 0x7E9 к немодифицированной прошивке (`tests/dq250_boot.rs::dq250_uds_probe`, плата
одна; `studio::tcu_io::tests::dq250_workshop_scenario`, ЭБУ + ТКУ + plant). Тестер — оборудование стенда (как VCDS/ODIS);
всё решает прошивка.

**Диспетчер** (`VERIFIED-S`): таблица сервисов 0x800C4AF8, записи по 12 Б (SID, обработчик, флаги): 10 → 0x800982E0,
19 → 0x800419D4, 22 → 0x8009C8B0, 27 → 0x800A42F4, 28 → 0x8006B8E8, 2E → 0x800927E0, 31 → 0x8005B0A8, 3E → 0x800806E0,
85 → 0x80063474; у 11/14/23/2F/34..37/3D/86/87 обработчика нет. Сессии — таблица 0x800C4BEC (01, 02, 03, 40, 4F), текущая
0xD0003666; `10 03` → `50 03 00 32 01 F4` (`VERIFIED-T`). Чтение `22`: DID = (тип, индекс), обработчик по типу (тип 1 →
0x8004BFC4: 0x0102 статус процедуры, 0x0103 счётчик неудачных ключей, 0x0105 номер процедуры; тип 6 — 0x0600).

**Доступ 27** (`VERIFIED-S`, ключ `VERIFIED-T`): seed `27 03` = 0xD0000428 (0x1B5E69A3, если 0), key = seed + 0x0010829B
(big endian); неверный ключ → NRC 0x35, счётчик в младшем полубайте 0xD0004322 (в NVM), с 3-й ошибки флаг задержки
0xD000434C. Для кодирования и базовых установок не требуется (`VERIFIED-T`).

**Кодирование** `2E 0600` (0x800927E0, `VERIFIED-S/T`):
- данные — 2 байта, число в десятичной записи (VCDS показывает его как «000024» = 0x0018); каждая из 5 цифр (с младшей)
  не больше таблицы 0x800C1E30 = 7, 2, 0, 9, 0, иначе NRC 0x31; в сессиях, кроме CAL 0x80034C2F (= 03) и 0x4F, две
  младшие цифры должны совпадать с CAL 0x80034C04 (= 20) или отличаться от записанных на кратное 100;
- нужен предшествующий `2E F198` (6 Б кода мастерской → 0xD0004178, флаг 0xD0005F84), иначе NRC 0x24 (`VERIFIED-T`); 0xD000043F
  ≠ 0, иначе 0x22;
- записывается 0xD00042AC (кодирование) + копия F198 0xD00042B0, запрос NVM (0xD0005F7C бит 1) → EEPROM: две копии по
  13 Б 0x1C4 / 0x1D1 (кодирование u32 LE, F198, счётчик, CRC) сразу после ответа (`VERIFIED-T`);
- стёртая микросхема: прочитанное кодирование = 20 (CAL 0x80034C04).
- Смысл цифр не разобран (не проверено). Кодирование стенда 000024 (по исходным данным, со считанной машины не
  проверено) отличается от CAL-значения 000020 младшей цифрой.
- Студия: `write_coding` = `10 03`, `2E F198` (`BENCH_WORKSHOP_CODE` 00 00 00 00 00 01 — раскладка полей у настоящих
  тестеров `UNVERIFIED`), `2E 0600`, `22 0600`. Принято, переживает выключение зажигания и перезапуск ТКУ (`VERIFIED-T`).
- События 0x121 / 0x167 («P0602») кодированием не снимаются: 0x167 — вход AIN25 (§6, снято подачей входа), 0x121 —
  адаптация точек касания (§7).

**Процедуры** `31 01 <rid> 04 00 00` (0x8005B0A8, `VERIFIED-S`; запуск/статусы `VERIFIED-T`):
- опция обязана быть `04 00 00` (иначе 0x22); пока предыдущая процедура не завершена тестером (`31 02 <rid>`), новая —
  NRC 0x24; `31 03` не поддерживается (0x12) — статус читается `22 0102`: 0xC0 выполняется, 0x10 успешно, 0x60 не удалась,
  0x80 прервана, 0x00 нет (состояние 0xD0004122, номер 0xD0004120; автомат 0x80070540 по результату 0xD00059D8: 1/2/3);
- 0x0380 — адаптация актуаторов (вилок): каждый актуатор к обоим упорам, главное давление ~15.6 бар, сцепление ~1 бар
  проверяет, что передача включена; результат — флаги «положение передачи адаптировано» (0xD0004960 + 0x34·i + 0x32) и
  конечные положения; ~73 с (`VERIFIED-T`);
- 0x04D4 — адаптация точек синхронизации: оба сцепления замкнуты (линия ~8 бар), валы на оборотах двигателя, каждый
  актуатор толкается к каждой передаче до блокировки синхронизатором (просадка оборотов двигателя), затем нейтраль с обеих
  сторон; проверка окон CAL 0x800383F0.. (шаг 9; вне окна — код 9 и событие 0x136); ~10.5 с (`VERIFIED-T`);
- сбросы адаптаций (только запись значений CAL / нулей, `VERIFIED-S`): 0x0317 (точки касания 0xD0003C34, 0xD0005CE0),
  0x0384 (вилки, 0xD0004960 ×4), 0x0386, 0x0388, 0x0389, 0x038A, 0x038B, 0x038C, 0x03B0 (прочие блоки; назначение не
  проверено); 0x0203 и 0x0301 (параметр 0x4451) — сервисные, не разбирались.

**Условия** (0xD00059B0, 0x8005B814, биты нарушений; маски допустимого — CAL 0x80038384, `VERIFIED-S`):
бит 0 — 0xD000331E < 10 (+0x1E); 1 — 0xD0003928 ≠ 0; 2 — |0xD0004AD8|/10 > 30 дольше CAL+0xE9 (0xD0004AD8 = выходные обороты
0xD000326A × коэффициент 0xD0003F6C, т. е. «автомобиль движется»); 3/4 — 0xD00031DE / 0xD00031E2 > 1500 (HYP: температуры
сцеплений, 0.1 °C); 5..12 — положение передачи i/стороны j не адаптировано (бит 9 — сторона N актуатора 5/N, передачи нет);
13 — обороты двигателя 0xD0003266 вне 600..1400 или стабильны < 100 циклов; 14 — `FUN_8007B534() = 0xA1` или
`FUN_8007FB48() = 0x54`. Запуск 0x0380 — маска 0x3FF8 (биты 0..2 и 14 должны быть сняты), 0x04D4 — 0x2218 (все положения
передач адаптированы); переход шага 2 → 3 — 0x1FE0 / 0x0200 (двигатель на холостом). Практически: двигатель на
холостом, P, тормоз, ATF прогрета, сначала 0x0380, затем 0x04D4.

**Хранение**: результаты базовых установок прошивка пишет в EEPROM при выключении зажигания (после-ход: 394–504 Б за
15 с, `VERIFIED-T`); при снятии питания без выключения зажигания они теряются (как у реального блока). Кодирование пишется
сразу. Студия держит EEPROM ТКУ между включениями (`StudioSession::tcu_nvm`, `TcuNvm`) и между запусками
(`build/studio_state/tcu_<id образа>.eeprom.bin`, не в git; файлы стенда не пишутся); лабораторная привязка иммобилайзера
переписывает запись IMO только если она отличается.

**Адаптация точек касания** (автоматическая, не базовая установка; §7): 0xD0003C85 / 0x800669AC, значения 0xD0003C34; на
стенде не стартует (условия 0xD0003C62).
